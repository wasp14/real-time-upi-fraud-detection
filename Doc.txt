# Why is recall low?

This is the key question.

I suspect one (or both) of these reasons:

### 1. Class imbalance

Your dataset is:

* Normal: 58,023
* Fraud: 3,114

Only about **5%** of transactions are fraud.

Without accounting for this imbalance, XGBoost tends to favor predicting the majority class.

### 2. Conservative decision threshold

By default:

```python
model.predict(X_test)
```

uses a threshold of **0.5**.

If the model predicts:

```
Fraud probability = 0.49
```

it is classified as **normal**, even though it might be suspicious.

Lowering the threshold (e.g., to 0.3) often increases recall, at the cost of more false positives.

---

# First improvement: Handle class imbalance

XGBoost has a parameter designed for this:

```python
scale_pos_weight
```

Calculate it like this:

```python
negative = (y_train == 0).sum()
positive = (y_train == 1).sum()

scale_pos_weight = negative / positive

print(scale_pos_weight)
```

For your data it should be roughly:

```
58023 / 3114 ≈ 18.6
```

Then initialize the model like:

```python
model = XGBClassifier(
    n_estimators=200,
    learning_rate=0.05,
    max_depth=5,
    random_state=42,
    eval_metric="logloss",
    scale_pos_weight=18.6
)
```

This tells XGBoost:

> "A fraud example is much more valuable than a normal example."

Usually this **improves recall significantly**.

---

# Second improvement: Probability-based predictions

Instead of:

```python
predictions = model.predict(X_test)
```

you can get probabilities:

```python
probabilities = model.predict_proba(X_test)[:, 1]
```

Then choose your own threshold:

```python
threshold = 0.3
predictions = (probabilities >= threshold).astype(int)
```

This lets you tune the trade-off between:

* Catching more fraud (higher recall)
* Raising fewer false alarms (higher precision)

# 1. `contamination`

This is **the most important parameter** in Isolation Forest.

It tells the algorithm:

> **"Approximately what fraction of my data should be considered anomalies?"**

For your dataset,

* Total transactions = **61,137**
* Fraud = **3,114**

Fraud percentage:

[
\frac{3114}{61137} \approx 0.0509
]

So we set

```python
contamination = 0.05
```

meaning

> "Around 5% of transactions are expected to be abnormal."

---

### What happens internally?

Isolation Forest assigns every transaction an **anomaly score**.

Imagine the scores are:

| Transaction | Score |
| ----------- | ----- |
| T1          | 0.02  |
| T2          | 0.11  |
| T3          | 0.73  |
| T4          | 0.95  |
| T5          | 0.35  |

The algorithm sorts them:

```text
0.02
0.11
0.35
0.73
0.95
```

If

```python
contamination = 0.20
```

then **20%** (the top 20% most anomalous) are labeled as anomalies.

In this example:

```text
0.95
```

would be classified as an anomaly.

---

### If contamination is too small

```python
contamination = 0.01
```

Only the most extreme transactions are flagged.

Result:

* High precision
* Low recall

---

### If contamination is too large

```python
contamination = 0.20
```

Now many normal transactions are also flagged.

Result:

* High recall
* Low precision

This is very similar to lowering the decision threshold in XGBoost.

---

# 2. `n_estimators`

This means:

> **How many isolation trees should the forest build?**

Just like Random Forest builds many decision trees,

Isolation Forest builds many **Isolation Trees**.

```
            Isolation Forest

        Tree 1

        Tree 2

        Tree 3

        ...

        Tree 200
```

Each tree looks at a random subset of the data and random features.

The final anomaly score is the average over all trees.

---

### Why use many trees?

One tree may isolate a transaction quickly by chance.

Many trees reduce randomness and produce more stable anomaly scores.

---

### Typical values

| Trees | Meaning             |
| ----- | ------------------- |
| 50    | Fast                |
| 100   | Standard            |
| 200   | More stable         |
| 500   | Usually unnecessary |

For your dataset (~61k rows), **200** is a good choice.

---

# 3. `random_state`

Machine learning algorithms often involve randomness.

Isolation Forest randomly chooses:

* features
* split values
* samples for each tree

Without

```python
random_state=42
```

every run may produce slightly different results.

Example:

Run 1

```text
Accuracy = 94.8%
Recall = 46%
```

Run 2

```text
Accuracy = 95.3%
Recall = 50%
```

Run 3

```text
Accuracy = 94.9%
Recall = 48%
```

---

With

```python
random_state=42
```

the randomness is fixed.

Every run produces the same forest and the same evaluation metrics, making experiments reproducible.

---

# Why "42"?

There's nothing mathematically special about 42. It's a long-standing programming tradition (popularized by *The Hitchhiker's Guide to the Galaxy*). You could just as well use:

```python
random_state=7
```

or

```python
random_state=123
```

as long as you use the same value consistently.

# Other useful parameters

These aren't required now, but it's good to know them.

### `max_samples`

How many training samples each tree sees.

```python
max_samples=256
```

Each tree trains on 256 randomly selected transactions.

If you set:

```python
max_samples="auto"
```

Scikit-learn uses:

```
min(256, number_of_samples)
```

Since your dataset has over 61,000 rows, each tree will use 256 randomly chosen samples by default.

This makes the algorithm fast while still being effective.

---

### `max_features`

How many features each tree can use.

You have:

```
amount_ratio
time_since_last_txn
transaction_velocity
device_changed
city_changed
merchant_changed
```

So there are 6 features.

If:

```python
max_features=1.0
```

every tree can use all 6 features.

If:

```python
max_features=0.5
```

each tree randomly uses about 3 features.

Random feature selection increases diversity among trees.

---

### `bootstrap`

Whether trees sample **with replacement**.

```python
bootstrap=True
```

A transaction can appear multiple times in the same tree's training sample.

```python
bootstrap=False
```

Each sampled transaction appears at most once in a tree.

The default is `False`, and it's appropriate for most anomaly detection tasks.

# Why is it called SHAP?

It comes from **Shapley Values** in game theory.

Imagine four people lift a heavy table.

Who deserves the most credit?

You can't simply say:

> Alice lifted it.

Everyone contributed.

Shapley values calculate each person's **fair contribution**.

SHAP does the same for features.

Instead of people:

```text
device_changed

amount_ratio

velocity

city_changed
```

Each feature "contributes" toward the final prediction.

## I suggest we build SHAP incrementally

Instead of trying to generate every visualization at once, we'll proceed in this order:

1. **Load the saved XGBoost model**
2. **Create the SHAP explainer**
3. **Generate a Summary Plot** (global feature importance)
4. **Generate a Waterfall Plot** (explain one fraud prediction)
5. **Add SHAP explanations to the FastAPI inference service later**, so every prediction can include the top contributing features.

This approach keeps each step understandable and gives you useful artifacts at every stage.

# Step 2: The bottom number

At the bottom you see


This is called the **base value** (or expected value).

Think of it like this:

Before looking at **any** transaction, the model starts here.

Since most transactions are **normal**, XGBoost starts with a prediction leaning toward "Normal".

That's why the base value is negative.

**Important:** This is **not** a probability.

For XGBoost, SHAP shows values on the **log-odds scale** (the raw score before applying the sigmoid function).

# The biggest insight

This graph confirms something we suspected from the feature importance.

Look at the contributions:

| Feature             | Contribution |
| ------------------- | -----------: |
| amount_ratio        |    **+6.22** |
| device_changed      |    **+2.15** |
| time_since_last_txn |        -0.31 |
| city_changed        |        +0.11 |
| merchant_changed    |        +0.02 |
| velocity            |            0 |

This tells us that **for this particular transaction**, the decision was driven primarily by:

1. **Amount Ratio**
2. **Device Changed**

That's an important distinction:

* **Feature importance** tells you what the model relies on **across the entire dataset**.
* **SHAP waterfall** tells you why the model made **this one prediction**.

A feature can be very important overall but have almost no effect on a specific transaction if its value is ordinary.

# This is exactly what you'd say in an interview

Suppose an interviewer asks:

> "Why was this transaction classified as fraud?"

You could answer:

> "The model starts from the baseline expectation that most transactions are legitimate. It then evaluates the transaction's features. In this case, the amount ratio of **10.56** contributed the most toward the fraud prediction, indicating the transaction amount was much larger than the sender's typical behavior. The fact that the transaction came from a **new device** further increased the fraud score. Although the longer time since the previous transaction slightly reduced suspicion, its effect was much smaller. Overall, the positive contributions outweighed the negative ones, resulting in a very high fraud score."

That's exactly the kind of explanation SHAP is designed to provide, and it's much stronger than simply saying "the model predicted fraud."
