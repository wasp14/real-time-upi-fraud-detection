# Why is recall low?

This is the key question.

I suspect one (or both) of these reasons:

### 1. Class imbalance

Your dataset is:

* Normal: 58,023
* Fraud: 3,114

Only about **5%** of transactions are fraud.

Without accounting for this imbalance, XGBoost tends to favor predicting the majority class.

### 2. Conservative decision threshold

By default:

```python
model.predict(X_test)
```

uses a threshold of **0.5**.

If the model predicts:

```
Fraud probability = 0.49
```

it is classified as **normal**, even though it might be suspicious.

Lowering the threshold (e.g., to 0.3) often increases recall, at the cost of more false positives.

---

# First improvement: Handle class imbalance

XGBoost has a parameter designed for this:

```python
scale_pos_weight
```

Calculate it like this:

```python
negative = (y_train == 0).sum()
positive = (y_train == 1).sum()

scale_pos_weight = negative / positive

print(scale_pos_weight)
```

For your data it should be roughly:

```
58023 / 3114 ≈ 18.6
```

Then initialize the model like:

```python
model = XGBClassifier(
    n_estimators=200,
    learning_rate=0.05,
    max_depth=5,
    random_state=42,
    eval_metric="logloss",
    scale_pos_weight=18.6
)
```

This tells XGBoost:

> "A fraud example is much more valuable than a normal example."

Usually this **improves recall significantly**.

---

# Second improvement: Probability-based predictions

Instead of:

```python
predictions = model.predict(X_test)
```

you can get probabilities:

```python
probabilities = model.predict_proba(X_test)[:, 1]
```

Then choose your own threshold:

```python
threshold = 0.3
predictions = (probabilities >= threshold).astype(int)
```

This lets you tune the trade-off between:

* Catching more fraud (higher recall)
* Raising fewer false alarms (higher precision)

# 1. `contamination`

This is **the most important parameter** in Isolation Forest.

It tells the algorithm:

> **"Approximately what fraction of my data should be considered anomalies?"**

For your dataset,

* Total transactions = **61,137**
* Fraud = **3,114**

Fraud percentage:

[
\frac{3114}{61137} \approx 0.0509
]

So we set

```python
contamination = 0.05
```

meaning

> "Around 5% of transactions are expected to be abnormal."

---

### What happens internally?

Isolation Forest assigns every transaction an **anomaly score**.

Imagine the scores are:

| Transaction | Score |
| ----------- | ----- |
| T1          | 0.02  |
| T2          | 0.11  |
| T3          | 0.73  |
| T4          | 0.95  |
| T5          | 0.35  |

The algorithm sorts them:

```text
0.02
0.11
0.35
0.73
0.95
```

If

```python
contamination = 0.20
```

then **20%** (the top 20% most anomalous) are labeled as anomalies.

In this example:

```text
0.95
```

would be classified as an anomaly.

---

### If contamination is too small

```python
contamination = 0.01
```

Only the most extreme transactions are flagged.

Result:

* High precision
* Low recall

---

### If contamination is too large

```python
contamination = 0.20
```

Now many normal transactions are also flagged.

Result:

* High recall
* Low precision

This is very similar to lowering the decision threshold in XGBoost.

---

# 2. `n_estimators`

This means:

> **How many isolation trees should the forest build?**

Just like Random Forest builds many decision trees,

Isolation Forest builds many **Isolation Trees**.

```
            Isolation Forest

        Tree 1

        Tree 2

        Tree 3

        ...

        Tree 200
```

Each tree looks at a random subset of the data and random features.

The final anomaly score is the average over all trees.

---

### Why use many trees?

One tree may isolate a transaction quickly by chance.

Many trees reduce randomness and produce more stable anomaly scores.

---

### Typical values

| Trees | Meaning             |
| ----- | ------------------- |
| 50    | Fast                |
| 100   | Standard            |
| 200   | More stable         |
| 500   | Usually unnecessary |

For your dataset (~61k rows), **200** is a good choice.

---

# 3. `random_state`

Machine learning algorithms often involve randomness.

Isolation Forest randomly chooses:

* features
* split values
* samples for each tree

Without

```python
random_state=42
```

every run may produce slightly different results.

Example:

Run 1

```text
Accuracy = 94.8%
Recall = 46%
```

Run 2

```text
Accuracy = 95.3%
Recall = 50%
```

Run 3

```text
Accuracy = 94.9%
Recall = 48%
```

---

With

```python
random_state=42
```

the randomness is fixed.

Every run produces the same forest and the same evaluation metrics, making experiments reproducible.

---

# Why "42"?

There's nothing mathematically special about 42. It's a long-standing programming tradition (popularized by *The Hitchhiker's Guide to the Galaxy*). You could just as well use:

```python
random_state=7
```

or

```python
random_state=123
```

as long as you use the same value consistently.

# Other useful parameters

These aren't required now, but it's good to know them.

### `max_samples`

How many training samples each tree sees.

```python
max_samples=256
```

Each tree trains on 256 randomly selected transactions.

If you set:

```python
max_samples="auto"
```

Scikit-learn uses:

```
min(256, number_of_samples)
```

Since your dataset has over 61,000 rows, each tree will use 256 randomly chosen samples by default.

This makes the algorithm fast while still being effective.

---

### `max_features`

How many features each tree can use.

You have:

```
amount_ratio
time_since_last_txn
transaction_velocity
device_changed
city_changed
merchant_changed
```

So there are 6 features.

If:

```python
max_features=1.0
```

every tree can use all 6 features.

If:

```python
max_features=0.5
```

each tree randomly uses about 3 features.

Random feature selection increases diversity among trees.

---

### `bootstrap`

Whether trees sample **with replacement**.

```python
bootstrap=True
```

A transaction can appear multiple times in the same tree's training sample.

```python
bootstrap=False
```

Each sampled transaction appears at most once in a tree.

The default is `False`, and it's appropriate for most anomaly detection tasks.

# Why is it called SHAP?

It comes from **Shapley Values** in game theory.

Imagine four people lift a heavy table.

Who deserves the most credit?

You can't simply say:

> Alice lifted it.

Everyone contributed.

Shapley values calculate each person's **fair contribution**.

SHAP does the same for features.

Instead of people:

```text
device_changed

amount_ratio

velocity

city_changed
```

Each feature "contributes" toward the final prediction.

# Option 1 (Quick Fix - Recommended)

Modify your `docker-compose.yml`.

Under the **prometheus** service add:

```yaml
prometheus:
  image: prom/prometheus
  container_name: prometheus

  ports:
    - "9090:9090"

  volumes:
    - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml

  extra_hosts:
    - "host.docker.internal:host-gateway"

  restart: unless-stopped
```

The important part is:

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

This tells Docker:

> "Whenever someone asks for `host.docker.internal`, redirect it to the host machine."

Then restart Prometheus:

```bash
docker compose down
docker compose up -d
```

That means **Kafka is advertising itself as `localhost:9092`**.

Here's what is happening:

Kafka Broker

       │ Metadata response:

Producer

       │ Tries localhost:9092

# The fix

Change your Kafka service to advertise itself as `kafka`, not `localhost`.

Replace these two lines:

```yaml
KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
```

with

```yaml
KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
```

Also add:

```yaml
hostname: kafka
```

so your Kafka service becomes:

```yaml
kafka:
  image: apache/kafka:4.1.0
  container_name: kafka
  hostname: kafka

  ports:
    - "9092:9092"

  environment:
    KAFKA_NODE_ID: 1
    KAFKA_PROCESS_ROLES: broker,controller

    KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
    KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092

    KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
    KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
    KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
    KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT

    KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
```

---

# Then recreate Kafka completely

Because the broker metadata is persisted, don't just restart the container.

Run:

```bash
docker compose down -v
```

Then:

```bash
docker compose up -d kafka
```

Wait about 15–20 seconds.

Then verify what Kafka is advertising:

```bash
docker exec -it kafka /opt/kafka/bin/kafka-broker-api-versions.sh \
  --bootstrap-server localhost:9092
```

If everything is correct, the first line should now be:

```text
kafka:9092 (id: 1 ...)
```

**not**

```text
localhost:9092
```

Only after that should you run:

```bash
docker compose up --build producer
```
